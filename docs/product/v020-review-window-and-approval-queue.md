# v0.2.0 交接审阅窗口与操作恢复

## 修改

- OKR 交接从原请求生成开始保留固定 **5 分钟**审阅期限，App、SDK、Go 来源检查／物理租约和 Move 合约保持一致。页面显示原截止时间与分钟／秒倒计时；刷新、恢复和批准都不能续期。
- 审阅本身不授予执行权限。Host 接受后暂时保留实例；用户仍需分别确认审阅费用、执行约定审批费用，再明确继续。权限或 OKR 的剩余期限不足时，不能生成一个截短或已经过期的批准。
- 身份／组织创建的原交易已确认失败时，用户可以明确开始新尝试，再重新估算和确认费用。原摘要、实际 Gas、原生密钥和已创建 Human 保留。未知结果仍只查询原交易；多个窗口使用同一个后续请求 ID。
- 工作台和治理页从 Sui 读取 Agent 单次审批列表，打开固定实例的原消息处理。读取失败显示未知，陈旧审批保留来源／版本与原 Run，不提供失效执行入口。
- 独立代码审阅修复了零工具 Run 的预算资产判断、审批对象独立变化和旧实例／成员版本仍展示操作按钮的问题。
- 支持明确保存、恢复和删除未发送的本机草稿。每份草稿使用独立随机内容密钥、封装给原系统设备的公钥，作用域绑定链、Human、组织、Host 和具体实例；不会缓存执行授权。关闭或进入后台清除页面明文，保留已保存密文；缓存清除或丢失设备会丢失本机草稿。提交前先保存原请求标记，未知结果不恢复成新消息，不自动重发。
- Host 接受回应后同步显示原 Run 的已核验状态；剩余时间显示在 0–5 分钟范围，并明确为本机时钟估算，批准仍校验链上固定期限。

## 测试中保留的问题

- 第一次发布已确认，立即读取 UpgradeCap 时遇到对象暂不可见。后续只读核对原对象后继续，没有重复发布。
- 复用原云 Host 加入新测试组织时，正式 envd 先查询旧加入交易。localnet 已裁剪旧回执，流程正确停止为 unknown；本次没有生成 Host 加入签名或广播。新邀请尚未消费，其私密码未保存。没有清除旧技术日志或以当前成员状态伪造原交易回执。
- 为独立验证窗口，使用同一 Ubuntu 主机上的新隔离 Host profile。原未使用邀请已明确撤销；新邀请与新 Host 正式准入均确认，6 项核对通过。该测试不代表原 Host 的旧加入回执已恢复。
- 首次新邀请在连续报价时取得旧 Gas 引用，SDK 返回 unknown。只读查询后，本地 Sui 节点日志明确记录原摘要被全部验证节点以 `InvalidTransaction`／已消费 Gas 版本不可重试地拒绝；链上也没有新邀请对象。保留该证据，并读到前一笔撤销交易的新 Gas 版本后，才由测试操作者明确发起另一次报价。没有把 SDK unknown 改写成链上 failed，没有原字节重放；这是本地节点可观测的测试诊断，不是客户端自动重试策略。
- 新 worker 初始隔离配置误设 `sui.enabled=false`，启动检查拒绝并退出。修正为 `sui.enabled=true`、`runtime.chain_queue=false`、旧 mesh registry ID 空值后，正式运行时启动并认证 Coordinator；此前没有发现／执行实例或产生 Run。

## 普通刷新与已裁剪回执

实际安装版发现：成功提交常驻权限后，普通刷新先设为不可达，导致对话组件卸载、已确认回执从页面消失。重新打开时，本地测试链的原回执已经不可查询；只读检查证实技术日志保留原 `confirmed`、revision 2 和费用 21,499,860 MIST。服务公开接口观测到当时只有约 4.963 秒 checkpoint 历史；SDK 和 raw gRPC 都返回 NOT_FOUND，不是解析错误。

修复区分加载与真实读取失败；普通刷新保留对话，实际失联及权限变化仍使上下文失效。原权限回执仍保持不可查，不从当前对象拼造原回执。独立读取并核验同一实例的当前权限、版本已前进时，可以另发不同的新消息；原权限、未知消息、审批或 Run 不重试。两项新增回归检查这一区别，原摘要和技术日志保留。新 APK 实际保存同一草稿为新消息后，对话保持打开；草稿转为原提交标记，没有恢复成待重发内容。一次旧报价在点击确认前到期，UI 禁止提交，链上没有消息；明确取消并重新预览后才提交新请求。

## 多步骤对话的原请求保留

提交 `ac94273` 将未知的原消息、Run 和审批决定的公开请求定位独立保存，预览新步骤、取消费用或另一笔成功都不会清除它。新消息在预览与提交前重新查询原请求；同一消息任一方向的决定未知时，批准与拒绝均暂停。存储或查询失败保留限制，原交易日志不删除。

原成功 Run 的不可变结果已解密核验、对应预算声明已结算且当前权限仍有效时，允许独立新消息；历史消息到期只禁止复用旧请求。确定性步骤先查询自己的原请求，未知时不重新报价、签名或广播；不同的新步骤仍独立核验链上来源和费用。

## 工作台审批对话的生命周期

实际安装版在批准单次文件写入后又发现队列刷新会卸载卡片内对话；执行权限已确认后也丢失了页面候选 ID，重新读取时原回执已被测试链裁剪。原消息到期时尚无 Run、没有派发，独立云端检查确认目标文件不存在；到期后的执行入口保持禁用。

审批对话现由队列外的独立容器持有。同一来源刷新保留已读列表；加载、筛选、审批结果变化与部分读取失败都不会关闭正在处理的对话。每项操作仍读取当前链上授权；组织或身份变化及明确关闭继续清除页面明文。旧失效请求与未知回执保留，不用重复签名补回页面状态。

## 云端 direct 窗口与新实例导入

新 direct 消息使用合约已有的固定 5 分钟上限，同时受权限、Host 成员及设备授权更早截止时间约束。审批、Run 准备和 Host 执行共用原截止时间；费用预览也占用该窗口。App 显示设备时间估算的倒计时，签名前后及各阶段仍核验原期限，原消息或原报价不能续期。

一次原单次写入在云端核验期间过期，已失败结算为 0 次工具调用，独立检查文件不存在。随后 [envd 读取优化](v020-direct-cloud-read-performance.md)减少同一次解析的读取往返，保留全部授权阶段和末尾最新版本复核；r13 的新请求已实际读／写 2 次，但在第三次复读前到期，失败结算为 2／0，原副作用保留。完整成功的新写入仍等待具体用户授权，详见[实际 UI 报告](evidence/v020-installed-ui-acceptance.md)。

envd 重启会产生新的 physical instance。导入技术记录现按链、Human、组织、Host 和实例隔离；同一实例换 workspace 或 Coordinator 不能借此绕过原未知请求。旧组织级 v1 记录保留独立只读查询入口。恢复确认回执必须与当前选择的 Host、实例和 workspace 匹配，目标切换使原会话与费用预览失效。新实例仍从仅观察导入开始，随后明确确认控制。

## 较新 OKR 的独立暂停

安装版实测暴露：新 OKR 已完成规格修改与控制批准，当前为 ACTIVE v3；原 v1 规格修改交易因节点历史裁剪而返回 unknown，旧 UI 因此连新暂停也禁用。原交易摘要与旧版本定位保留，不能作为再次修改的理由。

修复仅允许同一 OKR 的较早 pause／replace 请求，在最新链上 ACTIVE 版本严格推进后，单独预览新的 pause。原请求保持原状态；新操作仍检查 operate 权限、原约定及预期版本，并在报价和签名前后复核。原版本未知请求、stop／replace、读失败或不同来源均不适用。公开请求定位历史追加保存，报价、取消、重开不会覆盖旧 unknown。

专项 **45/45**、完整 App **337/337**、严格 TypeScript 和独立复核通过。r8 安装版已在同一 OKR 成功暂停：v3→v4、约定 v2→v3、工具 0／0、无 KR 执行；原 v1 修改回执仍显示 unknown，新 pause 回执独立 confirmed，弹窗保持打开。随后单次审批写入与缓存恢复见[UI 验收](evidence/v020-installed-ui-acceptance.md)。

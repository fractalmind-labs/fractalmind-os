# v0.2.0 App：OKR 技能上下文与显式提案

依据 #39/#27/#28/#34、PRD v0.11 和原型 v2。基线 `774ef9c`。
本增量实现原生 App 的实际导出、提案导入、变更审阅、费用确认和签名提交；完整 #40 仍未完成。

## 操作流程

工作台和 OKR 详情增加「技能上下文与提案」。解锁具有当前读取权限的设备后，读取链上规格、KR、约定、原执行、预算及验收来源。明确确认明文导出后下载 `OKR.md`，由用户保存到为 Agent 批准的工作目录。此操作不支付 Gas、不写入 Host、不启动 Agent。

文件包含两个 JSON 区块：

- `fractalmind-okr-snapshot`：网络／链标识、两个原始包、组织／Human／OKR、逻辑版本、正文记录及修订、密钥版本和读取时间；完整规格、KR 样本／证据／验证 ID、已批准文件计划、工具边界、原审批 ID、预算支出与在途预留、原 Run 和最终验收来源。
- `fractalmind-okr-proposal`：可编辑的目标、成功标准、优先级、期限、目录、禁止动作、总工具预算和 1–3 个 KR。指标使用精确十进制字符串；链上事实保留原始定点整数和采样时间，不把未知值写成零。

Agent 只修改提案区块，再由用户选择文件导入。导入刷新当前事实，显示 CLEAN／UNSUBMITTED 和逐字段的原值／提案值。链上事实、来源和说明不能通过文件修改；Windows CRLF、JSON 缩进及键顺序变化不影响含义。文件上限为 256 KiB，过大的上下文显式拒绝。

用户先审阅 KR 重置及累计预算影响，再预览费用并明确签名。只允许草稿／暂停且旧控制执行结清的目标替换规格；沿已有正式 `OkrIntervention` 路径核验权限、版本、原预留、实际已用和报价来源。替换后保持草稿／暂停，须重新 Host 审阅及独立批准执行约定。此控制器没有投递、验证 KR、验收或自动恢复接口。

原请求 ID／摘要保存在技术 journal；重新打开先查询，未知结果不能成为重试理由。报价或签名前来源变化会拒绝；关闭、隐藏、切换目标或设备到期清除页面私有内容。浏览器公开身份连接不能解密、导出私有上下文或签名。

## 约定来源

ACTIVE／已验收目标的文件计划检查原 Host 接受签名、规格记录、组织／实例／成员、工作区、预算、当前链上 policy 的 proposal hash 和具体目录边界。Host 审阅的实例版本是批准前版本，链上约定绑定批准后的 `+1` 版本；最终验收推进约定版本后，历史批准仍作为原来源读取，不授予新执行权限。暂停目标的已失效计划不投影为当前已批准计划。

异步证明核验后，正式读取控制器再次核对原权限、来源、原 Run 状态及预算。投影是历史上下文；执行端仍必须重新读取资格和逐次工具边界。修改本地读取时间、状态或文件不能成为执行资格或新的观测。

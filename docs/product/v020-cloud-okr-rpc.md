## 测量与修复

云上通过原 SSH 回环隧道读取原 Sui 对象，单次读取热态约 **465–694 毫秒**，首次连接 **1,557 毫秒**。正式 Go 来源校验对同一原 Run 做三轮交替只读对照：

| 来源读取     | 网络请求             | 三轮耗时（毫秒）     | 中位数     |
| ------------ | -------------------- | -------------------- | ---------- |
| 逐项版本复查 | 13 次单项            | 11,176／6,406／6,583 | 6,583 毫秒 |
| 批量版本复查 | 7 次单项＋1 次 batch | 7,210／4,833／4,234  | 4,833 毫秒 |

中位耗时下降约 **26.6%**。六次读取都恢复精确原 Run 和 RUNNING 状态，没有交易或执行。该对照测量的是读取，不是完整任务耗时。

代码变更：

1. 原始 Move BCS 的最新对象复查使用 gRPC `BatchGetObjects`，每批最多 32 项；ID、顺序、数量、版本、单项错误均校验，失败不退回旧值或其他传输。
2. 一次权限解析内，已知且相互独立的对象可批量读取，仍逐项验证类型、所有者、UID 与布局，并在返回前复查全部版本。数据仅在本次调用内使用。
3. 交接审阅保留初次类型校验的私有依赖集合，结束时复查完整版本集合，避免再次读取／解码相同依赖；再读链上 Clock，网络等待跨过有效期时拒绝。
4. gRPC 单次调用最多等待 30 秒，保留调用方更短的期限／取消。对**已经成功广播的原开始／结果交易**只读确认窗口从 5 秒调整为 30 秒，始终检查精确原 Run、attempt 和摘要，不补发。

测量表明原 5 秒读取窗口不足以稳定覆盖真实网络；它是此次开始未确认的合理原因。原 Host 的详细拒绝响应未在 HTTP 超时后保存，不能据此声称完整定位了原执行失败原因。命令权限、55 秒审阅提案、最多一分钟的物理审阅租约和逐次工具检查保持。

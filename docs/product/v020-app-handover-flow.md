# App 纳入 OKR：观察权限、审阅与审批界面

依据 PRD v0.11／原型 v2 的 J11，承接[原审阅票据](v020-app-handover-review.md)与[原生审批](v020-app-handover-approval.md)。正式客户端在受管理实例卡片新增“纳入 OKR”，接通现有控制器。**界面接线不代表安装后全流程或完整 v0.2.0 已验收。**

## 当前流程

1. 选择组织内草稿／已暂停 OKR，通过当前原生设备读取并解密规格。当前实例必须是 `bounded-process-v1`，成员与活跃 Host／实例指针必须匹配；完整执行目录有未结控制执行则拒绝。tmux 继续仅观察。
2. 填写每个 KR 的具体文件路径、目标内容与工具次数，检查指标、允许目录、禁止动作、预算及期限。当前受约束文件执行器支持 1–3 个顺序文件计数 KR，每个 KR 1–3 个文件、基线为 0；不能执行的自然语言约束保留并拒绝授权。人的目标／内容审核仍不可由路径校验替代。
3. **独立确认观察权限费用**：`HandoverSetup` 签发绑定当前设备／实例的一次 status 观察能力，零工具预算，最长 10 分钟且不超过成员／设备期限。报价不会签名、预留 Run、派发 Host 或授予控制。确认回执按准确创建类型、输出版本与原对象创建交易核验能力 ID。
4. **独立确认审阅准备费用**：正式工厂从当前链上版本和解密规格构造提案；若当前规格与界面刚读取的目标／约束不同，即使文件指标相同也拒绝。原生签名后再次核验。`HandoverReview` 原子保存精确加密计划／签名命令票据、结果密钥与原观察 Run。报价和原生签名前／返回后复核当前来源。
5. 明确发送原观察命令给 Host，读取原 Run 的接受证明。投递尝试先保存可丢弃的技术标记；丢失回应只查询原请求。界面不自动重发，甚至预检失败后也保守保持“已尝试”。这一传输策略尚需真实 envd／安装后联测。
6. **独立确认约定审批费用**：从原 Run 验证 Host 签名、有效期与原提案后调用原生审批控制器。审批同一交易保存约定／政策并激活 OKR，不派发继续。独立明确继续界面及原生 runner 接线仍待完成。

三次费用确认分别显示当前网络、付款地址、SUI 余额、模拟费用、Gas 上限与报价到期时间；费用与实际 Run／工具预算分开。原未知／失败／确认摘要均优先查询，不能因权限变化或缺少查询结果自动替换原交易。

## 恢复与界面寿命

界面保存的设备配置／attempt UUID／Grant ID／能力 ID／投递尝试标记都是技术关联信息，不是授权或业务正文。目标、具体计划、密文记录、原签名请求、Run 与执行约定以 Sui 为权威；未提交的表单和报价只在内存。

“恢复原审阅”读取同一原票据；“从链上查找审阅”列出当前 checkpoint 目录中的审阅键，选择后按原控制器解密、核验实例和唯一原 Run。默认恢复不派发／审批。目录未观察到行、原交易裁剪为 unknown，都不证明操作未发生。查找界面尚未在安装后实际清空缓存旅程验收，跨设备原证明的审批限制仍需覆盖。

关闭、切换上下文、隐藏页面或卸载组件会清除私有表单并失效原生调用范围。`scopedNativeInvoke` 在原生调用前与返回后检查范围；SDK `assertBeforeBroadcast` 在签名验证后、持久日志 claim 完成后且实际广播前分别同步核验，覆盖关闭发生在系统签名或日志落盘等待中的情况。claim 已完成后的拒绝保留原 pending 摘要／Gas 关联，结果继续查询为 unknown，不能静默重放；其人工解除流程仍需完善。每个依赖链读取返回后也检查当前窗口范围。组件以稳定组织／实例 ID 挂载，常规 15 秒刷新不会因整个快照变化丢失正在确认的流程。

审阅目前采用原协议的 55 秒提案窗口，不静默续期。尚未尝试提交的候选允许明确重新准备；提交之后的过期／失败新审阅及原排队观察结清界面仍需补齐。当前“设备密钥配置”选择仍是技术入口；面向用户的设备选择应随安装后旅程改进。

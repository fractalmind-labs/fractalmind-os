# v0.2.0 直接消息与常驻权限：当前实现和发布门禁

依据 PRD v0.11、原型 v2、#41/#43/#45。完整 v0.2.0 目标保持不变。此增量是协议和 SDK 基础，直接对话尚未接通 envd 和正式 App 界面。

## 已实现

- 每个受管理 Agent 一份版本化常驻权限，包含动作、路径边界哈希、固定工具预算上限、已用／在途预留、有效期、批准设备。换版保留累计支出与预留。只有有 approve 权限的设备可以修改；仅观察实例不能创建执行权限。
- 消息固定组织、Human、Host 成员、受管理实例、设备／Grant、权限版本、会话和消息标识。正文以加密产品记录持久化。请求内容哈希同时绑定实际消息、任务、动作、路径集合和工具预算，防止换一个有效签名后把原消息指向另一条指令。
- 单次审批绑定原消息、实例、版本、动作、路径、预算及工作区占用版本；批准与消费分开，准备原 Run 时原子消费。单次批准单独记账，不增加常驻预算或清空原支出。
- 直接消息复用 RemoteCapability、CommandExecution、不可变加密结果和实例执行目录。一个消息只关联一个原 Run；相同命令返回原 Run。未知结果保留预算及未结执行，历史终结或排队取消可以结清旧版权限的预留。
- 工作区占用索引记录 Agent 和「Host 地址＋工作区哈希」。同一 Host、同一目录中的不同实例共享写保护；其他 Host 上的同名目录分别判断。旧 ACTIVE OKR 未被索引覆盖时，工作区覆盖为未知。审批不能把未知覆盖变成允许写入。
- 旧通用 Agent 命令准备和开始入口拒绝 direct.message，必须通过绑定常驻权限的入口。
- SDK 提供权限／消息／审批构建、类型化 BCS 读取、链上消息目录和签名命令准备。准备前核对原消息、内容哈希、目标、当前成员及实例、权限版本、Capability、预算和审批绑定。不签名、不派发、不重试，不改变 OKR 预算。

当前动作模型为 ask、status、file.read、file.write。声明模型不代表适配器已经支持对话。envd 尚未实现直接消息接收与每次工具前的权限检查，App 也尚未显示可执行的直接对话入口。当前控制资格来自已审阅的 OKR 交接；首次不依赖 OKR 的直接纳管交接仍需实现。

## 验证范围

[专项与回归](evidence/v020-direct-permission-unit.json)：Move **140/140**（新增 **18** 项），SDK **136/136**（新增 **8** 组），App **146/146**；SDK 类型／构建、App 生产构建和联测脚本严格类型通过。

Move 覆盖预算预留、重复请求、单次消费、单独结算、换版保留支出／预留、旧请求及旧审批拒绝、未知结果、原排队退款、精确到期、批准设备 Grant 换版、工作区变化及通用入口绕过拒绝。Host 入网及物理同意在这些单位测试中使用明确标注的 test_only 夹具；这些夹具不进入发布字节码，不能作为入网签名和真实接管的证据。

SDK 验证签名与内容／实例／版本／预算绑定、链对象来源及不可变性、审批来源、撤销状态、读取期间目录变化、未知预算与生命周期参数。失败测试先有通过的基线，并断言具体拒绝原因，防止无关夹具错误被计为安全检查通过。

## 实际发布被拒绝

[发布体积证据](evidence/v020-direct-package-size.json)：对当前完整零地址测试包进行构建后，使用隔离 localnet 和临时测试账户发布。**发布模拟失败，未广播发布交易**：

- 21 个模块的原始字节码合计 **108,033 bytes**。
- Sui 检查的包对象大小 **116,714 bytes**。
- 当前验证器上限 **102,400 bytes**。
- 原错误：MovePackageTooBig。

编译和单位测试通过不能证明包可发布。因此这次增量没有新的真实链直接消息证据。已有两个 KR 与原生人工验收报告属于之前的包，不能用于证明新模块可部署。

联测脚本新增 --direct-permission，要求同时使用 --human-sequence。预定验证实际 OS 加密消息、类型化目录、普通／单次审批 Run 预留、权限换版及历史取消；不投递 direct.message。该新增分支目前仅通过严格类型检查，尚未成功运行。部署脚本保存模拟拒绝或原报价／摘要，已有输出不得覆盖或自动重发。

## 下一步必需工作

1. 将直接交互协议拆为独立包，保持原核心包的公开 ABI。不能删掉旧模块，或通过修改本地验证器上限绕过发布门禁。
2. 核心包继续负责 Human／DeviceGrant、成员与实例、Capability、Run 和预算的统一校验。扩展调用需要核心生成、不可伪造且绑定扩展来源／合同的授权凭证；保留当前内部接口的封装边界。不能直接公开任意组织 UID 写入或未验证的授权记录写入接口。
3. SDK、App 部署信息、BCS 类型来源及 envd 读取／投递明确区分核心包和扩展包。验证旧对象仍可读取和结算、其他包无法伪造扩展授权，以及两个完整包各自能在原大小限制下发布。
4. 完成真实 SDK／原生密码链路验证，再接通 envd 每次工具前校验、消息回执、正式对话／审批 UI、固定实例离线、介入后恢复和消息转 OKR 草稿。

完整自主推进、技能投影、清缓存／重启恢复、安装后 UI、云 Host 和手机核心旅程仍按 #40 验收。

# v0.2.0 OKR 模型与验收增量

此增量推进 #27/#28/#34/#37，新增 `okr::Okr` 和 SDK `okr` API。既有 `objective::Objective`、`KeyResult` 和 Run 对象字段不变；新模型需要包含 `okr` 模块的协议包。当前独立本地链发布和验证通过，既有已发布包的升级部署仍待验收。

## 链上模型

组织动态字段 `okr::IndexKey` 保存 OKR 目录和 ACTIVE 计数；目录以逻辑 ID 映射共享 OKR。创建同时保存加密规格与类型化指标。相同逻辑 ID、Human 和创建内容的精确重试返回原 ID；冲突内容拒绝。目录可以分页重建，无需保存 OKR 对象 ID 清单。

| 状态 | 语义 |
| --- | --- |
| DRAFT | 已持久化的候选，可以修改成功标准和指标 |
| ACTIVE | 人已确认，绑定一个真实纳管实例和约定，最多同时三个 |
| PAUSED | 暂停、释放 ACTIVE 名额，提升约定版本；修改后须重新激活 |
| ACHIEVED | 每个 KR 已验证，且人另行确认整体成功标准 |
| ARCHIVED | 停止继续操作，历史正文、Run 和观测仍保留 |

Human／DeviceGrant 权限在每次变更时检查。规格、激活、KR 验证、整体验收与归档需要审批权限；暂停需要操作权限。规格、生命周期、观测及验收变更校验 `expectedVersion`；执行命令另按签名意图、当前约定与 KR 游标校验。规格变化重置指标及顺序游标并提升约定版本；激活/恢复、暂停、达成、归档也改变约定版本。

规格含 1–3 个 KR。每个 KR 用一个非负 u64 固定精度指标，基线必须不同于目标、权重为 1–1,000,000、最大观测年龄为 1 ms–30 天。单位、精度、采样口径、验证规则及成功标准保存于加密规格，必须由客户端与类型化值一致构建。降低型指标由基线大于目标表示。

指标数值、采样时间、状态、对象关联和预算上限是公开链上字段。规格文字、工作区描述、约定正文、验证理由和成果验收正文加密保存。当前模型适合已明确使用公开数值的指标；私有数值及证明方案尚未实现。

## 运行约定与证据

激活读取真实 `HostMembership`、`CoordinatorBinding`、`ManagedAgent`，检查成员有效性和显式可控能力，固定一个实例、成员及版本、工作区摘要、边界摘要、预算资产/上限和期限。期限必须晚于 Clock 且不超过 OKR deadline。加密约定和 ACTIVE 计数在同一交易更新，第 4 个 ACTIVE 被原子拒绝。

Host 观测只能提交到当前顺序 KR。提交时检查当前约定版本、Host 和实例版本；必须提供相同组织、相同实例、激活后创建且已成功的真实 `CommandExecution`，以及该 Run 指向的不可变加密结果。观测时间不超过当前 Clock，符合新鲜度且不倒退。其他 Host、未知/失败 Run、错误证据对象、失效版本或越序观测拒绝。

观测保存两处：当前指标，以及不可变 `Observation` 历史。历史目录在 OKR 内可分页读取，记录 KR、约定版本、原始值、采样/录入时间、Run、证据和 Host。规格修改或归档保留原历史，工作台后续可从这些记录绘制实测趋势。Host 提交的值带来源归属且保持未验证；合约不能解密证据推断测量值是否真实。

人检查证据后显式验证当前 KR。合约检查有效、未过期的实测、证据与阈值；验证记录加密保存，顺序游标才移到下一 KR。所有 KR 已验证后仍保持 ACTIVE，需人另行检查整体成功标准、保存验收记录并执行 `achieve`。指标 100%、Run 成功和 Host 声明都不会自动达成 Objective。

SDK `metricProgress` 用 BigInt 计算提升/降低型进度并封顶；`weightedProgress` 归一化权重。缺失、未来或过期采样返回未知。图形进度与验证/验收状态分别展示。

## OKR 约定到实际执行

`okr::issue_capability` 创建绑定该 OKR、当前约定版本及边界摘要的执行权限。绑定以动态字段保存，保持既有 capability／Run／OKR 对象字段布局。动作固定为 `assign`、范围为 `control`，成员、实例、工作区、预算资产／上限及到期时间来自人批准的约定。

命令的签名载荷包含 `okr: { id, agreement_version, kr_index }` 和工具边界。路径集合使用域标记 `fractalmind.execution-boundary.v1`、按 UTF-8 字节排序的 BCS 向量及 SHA-256；摘要不含本次工具次数。SDK 与 Go 采用同一独立测试向量。envd 在获取启动资格前、每次工具调用和文件发布前核对载荷的路径摘要、当前约定／KR、实例、工作区、停止状态和链上 Clock。

绑定权限只能经过 `okr::prepare_command/begin_command/finish_command/request_stop`。通用 `node_execution` 的准备、启动、结算和停止入口对绑定权限拒绝（8321）；外部交易不能构造仅包内产生的 `ContractWitness` 来绕过检查。观测证据也必须来自同一绑定权限、约定及 KR。

### 共用预算

每个 OKR 通过 `BudgetKey` 保存预算总账和按 Run 索引的永久预留记录。不同 capability 共用 `spent + reserved <= limit`；权限换发和重新激活不会清零。准备命令同时预留两层预算，精确重试不再次预留。排队取消释放全部在途额度；运行中停止保持预留，Host 结果确认后结算实际成本；未知结果保留预留。预算返还不返还已使用次数或防重放记录。

暂停、换版或推进至下一 KR 后，旧命令不能取得新的执行资格，工具检查也会拒绝继续操作。已经启动的历史命令仍可提交结果和结算；历史读取核对原命令约定及两层逐笔账本，不要求旧约定仍可执行。预算一旦存在逐笔记录就不能改资产，避免破坏历史账本的含义；新上限不得小于已有支出与在途预留。

## 已通过验证

[真实本地链报告](evidence/v020-okr-lifecycle-localnet.json) 记录 105 笔 SDK 交易：73 成功、32 预期拒绝；其中 18 笔为新增 OKR 生命周期交易。复用真实原生文件 Agent：写入两个文件、Host 读取测量、生成加密成功检查点，然后提交观测，人工验证与单独验收。

验证了：四个可测量草案、精确创建重试、三个 ACTIVE、第四个拒绝且草稿未变、暂停释放名额、旧版本拒绝、其他 Host 不能提交、100% 实测仍未验证/未达成、人工 KR 验证后仍未达成、整体人工验收、从链上目录重建四个 OKR 和不可变观测。

消费式 Human 恢复及密钥轮换后，新 SDK 从恢复身份的组织目录找到已达成 OKR、重读观测，并解密 10 份 OKR 规格/约定/验证/验收正文。原有 8 份命令终态、12 个检查点和 6 份预算总账恢复检查继续通过。测试使用新生成的身份、独立本地网络和临时工作目录。

## 尚待贯通
